# Future multithreading suitability

Source-based assessment dated 29 October 2026, separate from the measured single-worker comparison. **No multi-worker ECS, shared-memory component store, Atomics protocol or parallel scheduler was implemented.** No parallel speedup is claimed.

bitECS 0.4.0 provides a more direct starting point for shared numeric processing. Its [threading guide](https://bitecs.dev/docs/multithreading) describes typed shared component stores, buffered queries and coordinating structural changes. Miniplex 2.0.0 uses ordinary entities and application scheduling, with no equivalent query-buffer API; see its [documented model](https://github.com/hmans/miniplex#differences-from-other-ecs-libraries). Neither automatically distributes systems across cores.

The [component guide](https://bitecs.dev/docs/component) distinguishes typed stores from object payloads. The tested Miniplex adapter uses `World<Entity>`, `with('active')`, explicit component mutation and game-owned IDs; the bitECS adapter owns per-world payload/numeric stores and entity-handle mappings. Exact package versions and lock/source fingerprints accompany the measured report.

## Domain dependency map

Treating the guide's “main thread” as the owning coordinator is this project's architectural interpretation. The locked source and the private-world worker churn tests support placing that owner in the simulation worker. This does not imply permission for helper workers to mutate the same world's internals concurrently.

The synthetic [`complete`](../../../../tools/ecs-bench/model.ts) function updates one processor's input/output/reservation state and shared completion, inflow and transfer counters. Those global counters cannot be concurrently incremented as ordinary object properties. A future implementation could use per-partition accounting and a deterministic reduction, but that adaptation and its conservation checks have not been built or timed.

The shared [`Base.commit`](../../../../tools/ecs-bench/base.ts) also touches owner inventory, deposit/pile quantities, the player contention fixture, membership, removed IDs and repaired ownership links. Shared stock spending remains explicitly ordered. That phase cannot be partitioned by processor index and assumed independent. Future real transport, recipe intake and ownership graphs may add further cross-entity dependencies; synthetic processor independence is not proof about unimplemented factory systems.

| Future work              | Potentially independent portion                                                              | Coordinator responsibility                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Processor work           | Per-processor work/charge and local buffer calculation, once its inputs/ownership are fixed. | Commit accounting once, resolve dependent transfers and preserve state transitions.                                                    |
| Movement calculations    | Candidate motion or other numeric calculations over disjoint data.                           | Resolve shared collision/occupancy constraints and apply authoritative results in a defined order.                                     |
| Inventory/recipe intake  | Read-only eligibility checks may be separable.                                               | Revalidate and commit stock transactions in manual, requested MiniFab, then Field Research priority.                                   |
| Structural churn         | Prepare plain replacement descriptions.                                                      | Allocate/recycle runtime handles, preserve stable game IDs, update membership and repair references after all relevant readers finish. |
| Presentation preparation | Produce a numeric presentation batch from completed state.                                   | Publish a consistent version, preserve removals/nested changes and keep presentation read-only.                                        |

These are design possibilities and dependency observations, not implemented jobs or estimates of achievable speedup. The current study's measured transport and system costs must be considered before assuming simulation parallelism would address its dominant cost.

## Migration touch points

For **Miniplex**, numeric helper jobs would require a new explicit mapping between plain entities and job-buffer indices, partition generation, result validation and write-back. Plain domain functions can remain useful, but any function that mutates shared resources needs an accounting/commit boundary. A custom buffer layer would need to preserve the simplicity that motivated the original selection.

For **bitECS**, the existing indexed numeric stores are closer to the desired shape. Changing their backing still requires capacity policy, shared-buffer lifetime, ID-reuse safety, membership/view refresh and a job completion protocol. Complex payloads and cross-entity transactions remain a separate design task. Its threading documentation reduces uncertainty about the intended pattern; it does not supply those project rules or prove the deployed browser can run them.

For **both**, future changes would affect candidate adapters/stores, scheduler dependencies, the command/result protocol, completed-view publication, capture/rebuild and tests. Avoid encoding one library's query/entity handles in public contracts now. A plain authoritative capture and stable IDs reduce coupling, but a future parallel implementation is not a drop-in configuration switch.

## Deployment and evidence limits

Shared memory needs cross-origin isolation and appropriate resource loading; see the [HTML structured-data rules](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializeinternal). A later design must check COOP/COEP, external scripts/assets, embedding, worker loading and development/production hosting. The isolated Angular packaging/CSP probe enables same-origin worker loading; it does not enable cross-origin isolation or change production headers.

The current browser measurements use object messages or an explicitly labelled transferred ArrayBuffer diagnostic. Future-readiness conclusions are architectural. Actual parallel scalability, break-even sizes, read/write contention, synchronization overhead, scheduling fairness, memory coherence and additional-core energy cost remain unmeasured.

**Future-readiness preference: bitECS**, if shared-memory numeric processing becomes a justified requirement. The current single-worker recommendation must still come from measured browser qualification and maintainability, with this preference presented as a separate tradeoff.
