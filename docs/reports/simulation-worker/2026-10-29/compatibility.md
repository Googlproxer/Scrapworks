# Session compatibility and production handoff

Source audit dated 29 October 2026. The isolated laboratory implements an asynchronous coordinator and transport. The production application still uses its synchronous plain-state session. The proposed changes below are a future implementation handoff, not changes already applied to the game.

## Proposed production contract

Keep input, commands and completed views as separate concerns:

1. Initialization submits plain `WorldDefinition`/content and resolves to readiness for one world generation.
2. The host submits the latest movement sample and ordered discrete commands. Commands carry stable IDs, and results identify acceptance/rejection and the completed tick.
3. One clock determines 50 ms steps. Start with host frame-driven credits; a worker-owned clock is a measured diagnostic, not a second simultaneous ticker.
4. The worker applies commands and ordered systems, commits structural changes and publishes completed views. Library handles stay private.
5. The host applies versioned changed records/removals to a detached cache. A missing base version requires resynchronization; intermediate deltas cannot simply be dropped.
6. Presentation reads the latest completed view and interpolates. Runtime/UI code must stop expecting a fresh authoritative result from the same synchronous `frame` call.
7. Pause/resume and teardown have explicit acknowledgements/revisions. No hidden-time catch-up or replay of stale continuous/discrete input is allowed.

The synthetic marker-command ledger proves transport sequencing; it does not implement future salvage/crafting/research commands. Shared synthetic inventory contention verifies domain spending priority separately.

The worker-owned clock remains a normal-world diagnostic. A source audit also finds that `Base.commit` appends removed IDs until publication clears them. Prolonged unpolled structural churn could therefore grow that removal log; this alternative needs a bounded coalescing/full-resynchronization policy before adoption. The default host-credit protocol bounds advancement between replies and does not have that independent-clock accumulation path. The diagnostic does not qualify a worker-owned clock for every workload or a prolonged host stall.

## Migration order and rollback

After reviewing the measured recommendation and any failed gates:

1. Resolve the publication/transport contract and production component/resource model before adding gameplay systems. Retain domain functions independent of the selected ECS.
2. Add plain asynchronous port contracts and a tested inline reference adapter. Define readiness, completed-view reads/subscription, command results, resynchronization and cancellation.
3. Adapt `GameRuntimeService`/`WorldSessionBridge` consumers to those semantics using the inline adapter first, retaining existing motor, lifecycle and input tests.
4. Add the worker-owned world and host coordinator. Instantiate one authoritative backend at a time; do not run mirrored inline and worker worlds in production.
5. Route activity/input revision changes and all pending requests through the new lifecycle. Verify hide/focus/modal/Inspector/controller transitions, async loading, Retry and repeated mount/unmount.
6. Bind the renderer to completed views, revalidate placement on authority and playtest real movement/camera/animation with interpolation. Prediction remains a later evidence-driven experiment.
7. Verify the real Angular/Babylon production bundle, worker URL/CSP/base path, accessibility, input latency, memory and target-scene frame times. The isolated packaging probe does not establish those runtime integration results.
8. Move only the adopted package into production dependencies when production integration is actually authorized and ready. Keep investigation code and competing libraries outside production inputs.

The rollback path selects the inline backend at session construction, using the same plain contracts and supported authoritative initialization/capture format. Replacing a running backend requires a completed-tick barrier and a complete validated capture; the presentation cache is insufficient. There is no transparent mid-failure fallback or guarantee of recovering uncheckpointed state. No rollback switch or production migration is implemented in this investigation.

Multi-worker ECS, shared-memory implementation and parallel system scheduling are excluded from this handoff's first implementation slice.
