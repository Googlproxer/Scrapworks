# Measurement method and evidence limits

The investigation compares Miniplex 2.0.0 and bitECS 0.4.0 in two configurations each: inline and one private ECS world in one dedicated browser worker. It reuses the existing native adapters, domain functions, deterministic seed 1729 and deep detached publication contract. Item quantities do not create entities. The normal target contains 100,000 meaningful entities, including 12,000 active processors, rich inventories, buffers, ownership, reservations, charge and histories.

## Cohorts

**Cohort A is exploratory scaling and diagnostic evidence.** Its planned 262 fresh-browser jobs comprise four correctness checks, 120 primary trials, four ancillary runs, 12 transport/batch trials, four instrumented memory runs, 108 paced runs, four timer-emulated 120 Hz runs and six worker-clock runs. The primary matrix has five repetitions of normal 50,000/100,000/250,000 worlds and idle/fully-active/churn 100,000 worlds, for all four configurations. A's disposable warm-up worker was terminated before measurement, so its worker trials do not establish warm-context qualification. Its planned worker-clock cases wait after reply completion and would use a different publication cadence; those cases were not executed after this confound was identified. Retain all results, failures and timeouts, without pooling them into corrected qualification.

**Cohort B supplies the corrected primary timing matrix.** It retains the warmed worker and initializes fresh measurement state within that execution context. All 120 primary trials, four correctness configurations and four untimed payload-size probes completed. It also separately times `MessageEvent.data` access and the whole receiver callback, explicitly acknowledges cancelled queued commands, and preserves accepted pending commands in captures. These common corrections do not change domain rules or numerical budgets. B was stopped after 168 jobs: its 40 completed paced cases used supplied RAF timeline intervals, which can remain regular while JavaScript callbacks arrive late. Those paced samples are archived and excluded from qualification.

**Cohort C supplies corrected browser responsiveness.** Its 128 jobs contain four correctness checks, 108 paced runs across all configurations/workloads/pressures, four emulated 120 Hz diagnostics and 12 paired host/worker-clock diagnostics at 8 ms host pressure. Qualification uses actual monotonic gaps between callback arrivals. Supplied RAF timeline intervals and callback lateness remain separate diagnostics. A deliberately injected 45 ms main-thread stall must be detected by the same recorder in every correctness job. Clock decisions and dispatch spacing use actual callback time; there is still one outstanding request under either clock.

B's complete primary timings and C's complete paced stage form the qualification evidence. A supplies separate CPU/memory/ancillary diagnostics. The report verifies unchanged primary timing code (SHA-256 `481cb8d367f830340ce8dab44a7c1d3a5dfb9160dcb35e8beeb4fcd485dfa84a`), unchanged core/domain/adapter/protocol sources, packages, numerical gates, hardware and environment labels before joining B and C. Their individual source manifests and completion-time source checks are retained. Superseded A timing and B paced samples are never pooled into qualification. The original four-candidate ECS report remains historical evidence and supplies no worker transport samples.

## Timing and qualification

Each job uses a fresh Chromium process. Jobs, builds and checks run sequentially. Each latency trial warms a disposable world for at least two seconds and 200 ticks, creates identical fresh measurement state, measures 2,000 fixed 50 ms steps without sleeping, and stops after a 120-second measured-trial limit. The first measurement-world tick is separate, so completed state contains 2,001 ticks for a successful trial. Checksums, canonical comparison, completed-operation arithmetic and payload-size estimates are outside timed regions.

Qualification uses the median of five independent per-run p95 and p99 values; individual repetitions and their range remain published. It requires simulation plus detached publication p95 ≤5 ms / p99 ≤8 ms, observed receiver work p95 ≤2 ms / p99 ≤4 ms, and all three normal paced repetitions at every host pressure to meet frame p95 ≤18.5 ms / p99 ≤33.4 ms and sampled-input-to-presentation p95 ≤100 ms / p99 ≤150 ms. Budgets were frozen after calibration and retained through the corrections.

`workAndPublication` times system execution, structural commits/dirty tracking, deep detached publication and any explicit wire packing inside the execution context. It excludes the subsequent `postMessage` call. Worker posting, host round trips and receiving work are reported separately. The combined duration is measured per sample; phase percentiles are never added to reconstruct a combined percentile. System/structural timers contain dirty tracking rather than claiming a separately isolated hot-path dirty-tracking cost.

`hostApply` covers explicit JSON decoding and detached-cache application. B's `receiveData` times the message-data getter; `observedReceiver` covers the whole message handler, including that getter, request bookkeeping and application. Work the browser performs before handler entry can remain unattributed. Frame intervals and monotonic host round trips include delivery. Per-frame accumulated observed receiver work and end-of-window outstanding probes are recorded. Cross-context epoch-aligned delivery estimates are diagnostic, with clock resolution/uncertainty, rather than the ranking clock.

The normal scheduler has one outstanding request, bounded discrete-command queues and one five-step credit allowance covering both dispatched and locally accumulated time. Bounded batch and yielding-batch variants are diagnostics. The worker-owned clock is an alternative, never a simultaneous second ticker. Pause acknowledges a completed tick; it cannot roll back an already running synchronous step.

## Responsiveness and presentation

Paced runs observe 30 seconds of headless Chromium callback arrivals after warm-up; the supplied RAF timeline is recorded alongside them. Controlled host work adds 0, 4 or 8 ms per callback. These figures qualify the standalone simulation laboratory, with observed browser cadence around 60 Hz; they do not establish physical-display, Babylon rendering or full-game performance. The 120 Hz timer scheduler is explicitly emulated diagnostic pacing.

Input probes are deterministic transport markers sampled on the host. The harness measures submission to applied-tick acknowledgement and the next DOM presentation callback. An acknowledgement produced synchronously within a callback is credited at the next callback, conservatively adding an interval to that inline proxy even though the text marker can update earlier. End-of-window pending probes include both unapplied probes and applied probes awaiting presentation; the latter equal the difference between applied and presented sample counts. Report these censored tails alongside the observed latency distribution. The probe does not measure physical input-to-photon delay or implement a real camera/animation playtest. Completed-tick interpolation is bookkeeping in the laboratory. Actual movement, collision, sprint/stop, input clearing and placement run through the existing Simulation/PlayerMotor in a separate 1,000-step worker/inline compatibility probe. Prediction remains deferred until a later integration demonstrates a need.

## Memory and transport

Instrumented runs are excluded from timing rankings. Each configuration receives a separate 10,000-tick churn soak and 20 create/capture/rebuild/dispose cycles. CDP attaches to both page and worker targets; page-only figures are never described as worker memory. Retained totals add reported JavaScript heap and backing storage per target. Allocation samples include collected objects and estimate allocation volume, not retained RAM. Browser process RSS and unsampled peaks are not substituted for retained-object evidence.

Collection occurs only at diagnostic checkpoints. CPU/allocation responses are serialized and released before retained-memory checkpoints. Heap snapshots bracket world disposal while the worker is still alive, followed by worker termination and lifecycle checks. GC traces include forced collections and overlapping events; their durations are not summed as unique pauses. Heap analysis counts concrete `entity-*` payload records, distinguishes compiler boilerplates, and retains relevant node/edge evidence. A finite stable soak does not prove all workloads leak-free.

Object messages are primary. The transferred JSON-buffer diagnostic includes encoding, transfer detachment and decoding, and is available to both candidates. B's detached-frame byte counts cover the initial full view, first normal tick and explicit dirty fractions. These are UTF-8 JSON estimates outside timing; actual structured-clone wire bytes and the later steady-state packet-size distribution are unavailable. Neither diagnostic changes the presentation contract or qualifies a new transport for adoption without further testing. No authoritative component store is transferred or shared.

Cold page load uses the common laboratory bundle, which contains both candidate APIs for the inline control and shared checks. Initial readiness includes full detached-view transfer. These measurements do not isolate a bare-library import or predict a future worker-only production bundle. The Angular production packaging probe verifies module-worker URLs, a deployed `/lab/` base path, strict same-origin CSP and accessibility. Production input auditing remains a separate check. The real game receives no ECS dependency or worker integration from this investigation.

Future multithreading suitability is assessed from locked source and official documentation in [future-threading.md](future-threading.md). SharedArrayBuffer, Atomics, worker pools, parallel systems and hosting-header changes are not implemented or benchmarked.

Worker-clock reply `workerPublication` fields time polling/publication, not the independently scheduled tick work. They are not used for CPU ranking; library CPU qualification comes from the complete B primary trials. Individual synchronous post durations were retained as per-run quantiles rather than a raw aligned series, so an exact combined worker-plus-post percentile is unavailable.
